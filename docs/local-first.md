# 로컬퍼스트 동기화 — 설계 검토

> 브랜치는 **목적이 아니라 수단**이었다. 목적은 "여러 기기에서 로컬에 쓰고 나중에 밀어 넣기"다.
> 이 문서는 그 목적을 기준으로 다시 검토한 것이다. 스레드/브랜치를 제품 기능으로
> 볼 때의 검토는 [git-concept.md](./git-concept.md)에 있고, 두 문서는 §7에서 만난다.

---

## 1. 전제를 다시 세운다

목적이 동기화라면 먼저 분리해야 할 것이 있다.

| | 제품 기능으로서의 브랜치 | 동기화 수단으로서의 브랜치 |
| --- | --- | --- |
| 사용자에게 | 보인다 (스레드 이름) | **보이면 안 된다** |
| 필요한 이유 | 메모를 묶어서 읽고 싶다 | 기기별로 갈라진 기록을 합쳐야 한다 |
| 없으면 | 그냥 평평한 타임라인 | 오프라인 쓰기 자체가 불가능 |

이 둘은 이름만 같을 뿐 다른 물건이다. **기기별 브랜치는 구현 세부사항이어야 하고
UI로 새어 나오면 안 된다.** 사용자가 "왜 내 메모가 폰 브랜치에 있지?"를 묻는 순간
설계가 실패한 것이다. 동기화는 성공했을 때 보이지 않아야 한다.

그래서 이 문서의 결론을 먼저 적으면:

> **git의 객체 모델은 로컬퍼스트에 정확히 맞고, git의 브랜치/머지 기계는
> 이 앱에 없는 문제를 푼다. 전자만 가져오고 후자는 버린다.**

## 2. git 모델 중 무엇이 살아남는가

### 살아남는 것 — 그리고 이게 핵심이다

**① 클라이언트가 ID를 만든다 (콘텐츠 주소)**

지금 코드에서 로컬퍼스트를 막는 결정적인 지점은 단 하나다.

```ts
// db/schema.ts:22
id: integer('id').primaryKey(),   // 서버 autoincrement
```

서버가 ID를 정하면 **오프라인 생성이 원천적으로 불가능하다.** 비행기에서 쓴 메모에
어떤 ID를 줄지 알 수 없고, 임시 ID를 줬다가 나중에 바꾸면 그 ID를 참조하던 모든
것(링크, 답글, 로컬 캐시)이 깨진다.

콘텐츠 해시(또는 UUIDv7)는 **서버와 조율 없이 전역 유일한 ID를 만든다.** git이
중앙 서버 없이 동작하는 이유가 정확히 이것이고, 로컬퍼스트가 필요로 하는 것도
정확히 이것이다. 이 하나가 git 은유의 실질적 값어치 전부라고 해도 과하지 않다.

**② 레코드가 불변이다 → 동기화가 멱등한 집합 합집합이 된다**

커밋이 불변이고 해시로 식별되면 동기화는 이렇게 된다.

```
sync = 서버가 가진 집합 ∪ 기기가 가진 집합
```

순서에 무관하고, 중복 적용해도 결과가 같고, 실패하면 그냥 다시 보내면 된다.
**불안정한 모바일 네트워크에서 정확히 필요한 성질**이며, 이것은 불변성에서
공짜로 따라 나온다. 반면 지금처럼 `UPDATE`로 행을 덮어쓰면 "이 UPDATE를 이미
적용했는가"를 따로 추적해야 하고, 재시도가 위험해진다.

**③ 부모 링크가 인과관계를 기록한다 → 충돌 감지가 공짜다**

각 리비전이 "직전 리비전의 해시"를 들고 있으면, **같은 부모를 가리키는 리비전이
둘 생긴 순간이 곧 충돌**이다. 별도의 버전 벡터나 충돌 감지 로직이 필요 없다.
git의 fork 감지와 같은 원리이고, 구현 비용은 컬럼 하나다.

### 버리는 것

**브랜치 ref, merge, 3-way 병합, conflict 해소 UI.**

이유는 단순하다. **개인 메모 앱에서 두 기기가 각각 다른 메모를 쓴 것은 충돌이 아니라
합집합이다.** git은 트리 전체를 병합하지만, 여기서 필요한 연산은 집합의 합집합이다.
3-way merge를 구현해서 얻는 결과가 set union이라면 노력 배분이 틀린 것이다.

진짜 충돌은 두 가지뿐이다.

1. 같은 메모를 두 기기에서 각각 수정
2. 한 기기에서 삭제 + 다른 기기에서 수정

이건 **메모 단위 LWW(last-writer-wins)** 로 끝난다. 개인용 단일 사용자 앱에서
사용자는 이 상황을 거의 만나지 않고, 만나더라도 "나중에 쓴 게 이겼다"가 기대에 맞다.

## 3. 진짜 비용 — RSC 아키텍처와의 충돌

스키마 컬럼 몇 개보다 훨씬 큰 비용이 여기 있다. 정직하게 말하면
**로컬퍼스트로 가는 것은 앱의 렌더링 아키텍처를 다시 짜는 일이다.**

현재 이 앱은 데이터 경로가 전부 서버에 있다.

```tsx
// app/components/CommitList.server.tsx:29 — 서버 컴포넌트가 Turso를 직접 조회
Effect.gen(function* () {
  const commitService = yield* CommitService
  const results = yield* commitService.getList({ ... })
})
```

로컬퍼스트는 읽기가 **로컬 저장소에서** 나와야 한다. 화면을 열자마자 네트워크 없이
그려져야 로컬퍼스트다. 그러면 필연적으로:

| 현재 | 로컬퍼스트 이후 |
| --- | --- |
| 서버 컴포넌트가 Turso 조회 | 클라이언트가 로컬 저장소 조회 |
| Server Action = 쓰기 경로 | Server Action/Route = **동기화 엔드포인트** |
| Turso = 유일한 진실 | 로컬 = 작업 사본, Turso = 공유 지점 |
| RSC 스트리밍의 이점 | 상당 부분 포기 (데이터 영역은 클라이언트 렌더) |
| PWA 없음 | 서비스워커 + manifest 필요 |

한 가지 유리한 점은 있다. **Effect는 동형(isomorphic)이라 서비스 계층을 클라이언트로
그대로 옮길 수 있다.** `CommitService`의 인터페이스를 유지한 채 `SqliteDrizzle` 대신
로컬 저장소 구현을 주입하면 되고, 이건 Effect의 의존성 주입이 원래 잘하는 일이다.
지금의 서비스 계층 구조가 여기서 값어치를 한다.

인증은 크게 안 바뀐다. `middleware.ts`의 `auth`가 그대로 동기화 엔드포인트를
보호하고, 서버는 세션의 `user_id`로 스코프를 거른다. 다만 **로그아웃 시 로컬
저장소를 반드시 지워야 한다** — 공용 기기에서 남으면 그대로 정보 유출이다.

## 4. 데이터 모델

핵심은 **정체성을 두 층으로 나누는 것**이다. 앞선 git 문서는 이 둘을 뭉뚱그렸는데,
동기화에서는 반드시 분리해야 한다.

```ts
export const commits = sqliteTable('commits', {
  // ── 정체성 ──
  hash: text('hash').primaryKey(),        // 이 리비전 = 커밋 (내용 해시)
  note_id: text('note_id').notNull(),     // 이 메모 (UUIDv7, 클라이언트 생성, 수정해도 불변)
  parent_hash: text('parent_hash'),       // 같은 note의 직전 리비전

  // ── 내용 ──
  message: text('message').notNull(),
  emoji: text('emoji').notNull(),
  deleted: integer('deleted', { mode: 'boolean' }).notNull().default(false), // 톰스톤

  // ── 출처 / 순서 ──
  user_id: text('user_id').notNull().references(() => users.id),
  device_id: text('device_id').notNull(),
  hlc: text('hlc').notNull(),             // 하이브리드 논리 시계 (LWW 정렬 키)
  created: text('created').notNull(),     // 표시용 벽시계

  // ── 서버 전용 ──
  seq: integer('seq'),                    // 서버가 insert 시 부여. pull 워터마크
})
```

- **`hash`가 PK다.** 그래서 push는 `ON CONFLICT DO NOTHING`으로 멱등해진다.
- **`note_id`는 수정해도 유지된다.** "어떤 메모인가"와 "그 메모의 어느 버전인가"는
  다른 질문이고, LWW는 `note_id`를 키로 묶어서 리비전 하나를 고른다.
- **`seq`는 서버만 부여한다.** 이것이 이 설계의 중심 분업이다 —
  **서버는 정체성을 정하지 않고 순서만 정한다.**
- 스레드(제품 기능)를 나중에 붙인다면 `reply_to_note_id` 컬럼을 하나 더 두면 된다.
  `parent_hash`(수정 이력)와는 별개의 관계이므로 섞지 말 것.

현재 화면의 목록 조회는 "각 `note_id`의 최신 리비전 중 삭제되지 않은 것"이 된다.

```sql
SELECT c.* FROM commits c
JOIN (
  SELECT note_id, MAX(hlc) AS hlc FROM commits
  WHERE user_id = ? GROUP BY note_id
) latest ON c.note_id = latest.note_id AND c.hlc = latest.hlc
WHERE c.deleted = 0
ORDER BY c.created DESC;
```

리비전이 쌓이므로 이 조회는 점점 무거워진다. 실사용에서 메모당 리비전은 1~2개라
당장은 문제없지만, `notes` 머티리얼라이즈드 뷰(최신 리비전만 담는 테이블)를
동기화 시점에 갱신하는 방식으로 나중에 분리하면 된다.

## 5. 동기화 프로토콜

git은 remote와 "공통 조상"을 협상하지만, **단일 사용자 + 단일 서버에서는 그럴
필요가 전혀 없다.** 서버가 순서를 매겨주므로 워터마크 하나로 끝난다.

```
GET  /api/sync?since=<seq>   → { records: [...], seq: <최신 seq> }
POST /api/sync               → { records: [...] }  (로컬에만 있는 것)
```

**Pull** — 클라이언트는 마지막으로 본 `seq`만 기억한다.
서버는 `WHERE user_id = ? AND seq > ?`로 그 이후 레코드를 준다.

**Push** — 클라이언트는 아직 서버 `seq`를 못 받은 로컬 레코드를 보낸다.
서버는 `hash` PK로 `ON CONFLICT DO NOTHING` insert하고, 새로 들어온 것에 `seq`를
부여해 돌려준다. 같은 걸 두 번 보내도 결과가 같으므로 **재시도가 안전하다.**

**충돌 처리** — push 결과에 같은 `note_id`·같은 `parent_hash`를 가진 다른 리비전이
있으면 갈라진 것이다. `hlc` 비교로 하나를 고르고(LWW), 진 쪽은 지우지 않고 남긴다.
남겨두면 나중에 "이 메모에 다른 버전이 있었다"를 보여줄 수 있고, 이건 불변 모델을
택한 대가로 공짜로 얻는 기능이다.

동기화 트리거는 앱 포커스, 온라인 복귀(`navigator.onLine`), 쓰기 직후,
그리고 주기적 폴링 정도로 충분하다. 실시간이 필요한 앱이 아니다.

## 6. 반드시 밟게 되는 함정 4가지

**① 톰스톤 — 삭제는 반드시 커밋이어야 한다**

행을 진짜 지우면, 오프라인에서 지운 메모가 다음 동기화 때 **되살아난다.**
(다른 기기는 그 메모를 여전히 갖고 있고, 삭제됐다는 사실은 어디에도 없으니까.)
로컬퍼스트 초심자가 100% 밟는 함정이다. 답은 `deleted` 플래그를 가진 리비전을
새로 만드는 것 — git이 히스토리를 지우는 대신 revert 커밋을 쌓는 것과 같은 답이다.

**② 시계 왜곡 — 벽시계로 LWW를 하면 안 된다**

기기 시계는 서로 다르다. 벽시계 기준 LWW를 쓰면 **시계가 빠른 기기가 항상 이긴다.**
하이브리드 논리 시계(HLC)를 쓴다: `(벽시계, 카운터, device_id)`를 문자열로 정렬
가능하게 인코딩하고, 다른 기기의 더 큰 시계를 보면 자기 시계를 끌어올린다.
구현은 50줄 정도이고 라이브러리도 많다.

**③ 스키마 버전 — 기기마다 앱 버전이 다르다**

한 기기는 업데이트했고 다른 기기는 안 했을 때, **구버전 클라이언트가 모르는 필드를
지워서 되밀어 넣는 사고**가 대표적이다. 동기화 레코드는 전방 호환으로 다루고
(모르는 필드는 보존해서 되돌려준다), 프로토콜 버전을 명시할 것.

**④ 로그아웃 / 계정 전환 시 로컬 저장소 삭제** — §3에서 언급한 그대로.

## 7. 두 문서가 만나는 지점

git 문서(제품 기능)와 이 문서(동기화)가 **공통으로 요구하는 것**이 있다.

- 커밋 불변성 (`UPDATE` 대신 새 리비전)
- 클라이언트 생성 ID / 콘텐츠 해시
- 부모 링크
- 톰스톤 삭제

**즉 어느 쪽을 택하든 이 4가지는 필요하다.** 그래서 지금 이걸 하는 것은 어느
방향으로도 낭비가 아니다.

반면 **`refs` 테이블·브랜치 UI·HEAD 전환은 동기화에 전혀 필요 없다.** 앞 문서의
3단계는 로컬퍼스트가 목적이라면 통째로 뺀다. 스레드가 제품 기능으로 여전히 갖고
싶다면 `reply_to_note_id` 하나로 충분하고, 그건 동기화와 독립적으로 언제든 붙일 수 있다.

## 8. 직접 만들 것인가, 엔진을 쓸 것인가

정직하게 — **동기화 엔진을 직접 만드는 것은 그 자체로 하나의 프로젝트다.**
위의 §5~6은 "핵심만 추린" 버전이고, 실제로는 로컬 저장소 추상화, 마이그레이션,
재시도/백오프, 부분 실패 복구가 더 붙는다.

먼저 확인할 것은 **이미 쓰고 있는 Turso**다. Turso는 임베디드 레플리카(로컬 SQLite
사본 + 동기화)를 제공하고 오프라인 쓰기 지원을 진행해 왔다. 이게 현재 브라우저에서
쓸 만한 상태라면 대부분의 작업이 사라진다 — `@libsql/client`가 이미 의존성에 있으니
가장 저렴한 경로다. 다만 임베디드 레플리카는 원래 서버/네이티브 환경 기능이라
브라우저에서는 wasm 경로가 필요하고, **내 정보는 2026년 5월 기준이므로 현재
지원 범위는 직접 확인해야 한다.** 여기부터 조사하는 것을 권한다.

그 외 후보군과 판단 기준:

| 부류 | 예 | 이 앱에 맞는가 |
| --- | --- | --- |
| SQLite 동기화 엔진 | PowerSync 등 | 맞음. 다만 백엔드 요구사항 확인 필요 |
| 동기화 프레임워크 | Replicache/Zero, Triplit, Jazz, Evolu, LiveStore | 맞음. 락인과 가격 구조를 볼 것 |
| CRDT | Automerge, Yjs | **대체로 과함** (아래) |
| 직접 구현 | §5~6 | 학습이 목적이라면 좋은 선택 |

**CRDT는 아마 과하다.** CRDT의 값어치는 *같은 문서를 동시에* 편집할 때 나온다.
개인 메모 앱은 append-only에 가깝고 단독 편집이 드물게 일어나므로 LWW로 충분하다.
(다만 Automerge는 불변 연산 히스토리라는 점에서 개념적으로 git과 가장 가까워서,
"git처럼 다루고 싶다"는 원래 동기와는 잘 맞는다. 태블릿에서 쓰던 긴 메모를 폰에서
이어 쓰는 시나리오가 중요해지면 텍스트 CRDT가 값어치를 하기 시작한다.)

**학습이 목적이라면 직접 구현을 권한다.** 이 프로젝트는 개인 메모 앱이고,
단일 사용자 · 작은 데이터 · 낮은 동시성이라 동기화를 직접 만들어보기에 거의
이상적인 난이도다. 실패해도 잃을 게 없고, 위 §5는 주말 몇 번 분량이다.

## 9. 단계별 경로

| 단계 | 내용 | 얻는 것 | 규모 |
| --- | --- | --- | --- |
| **0** | 소유권 검증 수정 + drizzle 마이그레이션 스크립트 | ([git-concept.md §8](./git-concept.md) 취약점 2건) | 작음 |
| **1** | **`id`를 클라이언트 생성으로 전환** (`note_id` UUIDv7 + `hash`) | 오프라인 쓰기의 전제조건. 이후 모든 것이 여기 의존 | 작음 |
| **2** | 불변 리비전 + 톰스톤 (`UPDATE`/`DELETE` 제거) | 동기화가 멱등해짐. 수정 이력도 덤으로 | 중간 |
| **3** | 아웃박스 패턴 (아래) | **체감 가치의 대부분이 여기서 나온다** | 중간 |
| **4** | 로컬 읽기 + PWA 셸 | 진짜 오프라인. RSC 재구성이 필요한 지점 | 큼 |
| **5** | 양방향 sync (`seq` 워터마크, HLC, 충돌 LWW) | 다중 기기 완성 | 중간 |

### 3단계를 특히 권하는 이유 — 아웃박스 패턴

진짜 로컬퍼스트(4~5단계) 전에, **1/5 비용으로 체감 가치의 80%** 를 가져오는 지점이 있다.

- **쓰기**: 로컬(IndexedDB)에 즉시 기록하고 UI를 바로 갱신 → 아웃박스 큐에 넣음
  → 온라인이면 백그라운드로 서버에 flush
- **읽기**: 서버가 여전히 진실. 로컬은 캐시(오프라인 읽기용)
- 머지 없음, CRDT 없음, 충돌 처리 없음

엄밀히는 "오프라인 대응"이지 "로컬퍼스트"가 아니다. 하지만 지하철에서 메모를 쓰면
즉시 저장되고 나중에 알아서 올라가는 **체감은 동일하다.** 그리고 1~2단계를 먼저
해두면 아웃박스는 자연스럽게 얹힌다 (클라이언트 ID가 있어야 낙관적 쓰기가 가능하고,
멱등성이 있어야 flush 재시도가 안전하기 때문이다).

**여기서 한 번 멈춰 실제로 써 보고, 로컬 읽기까지 정말 필요한지 판단할 것을 권한다.**
4단계는 RSC 구조를 되돌리는 작업이라 되돌리기 비싸고, 3단계까지의 이득이 생각보다
클 가능성이 높다.

## 10. 결정이 필요한 질문

1. **기기가 몇 대이고 정말 동시에 쓰는가?** 폰↔데스크탑을 번갈아 쓰는 정도라면
   충돌은 사실상 발생하지 않고, LWW조차 과할 수 있다.
2. **오프라인이 실제 요구인가, 즉시성이 요구인가?** "비행기에서도 써야 한다"와
   "저장 버튼 누르고 기다리기 싫다"는 다른 문제이고, 후자라면 3단계에서 끝난다.
3. **직접 구현 vs 엔진** — 학습이 목적인지 결과물이 목적인지에 따라 갈린다(§8).
4. **스레드는 여전히 원하는 기능인가?** 브랜치가 동기화를 위한 수단이었다면,
   제품 기능으로서의 스레드는 별개로 원하는지 다시 판단할 것.
