# 메모를 git 개념으로 다루기 — 설계 검토

원래 구상: **메모를 커밋한다 → 커밋은 참조 가능하다 → 참조로부터 브랜치(스레드)가 자란다.**

> **갱신 (2026-08-14)** — 이 문서의 데이터 모델은 처음에 정수 `id` 기준으로
> 쓰였는데, [local-first.md](./local-first.md)의 작업으로 정체성 모델이
> `hash`(리비전) + `note_id`(메모)로 바뀌었다. §4~5를 현재 코드에 맞춰 다시 썼다.
> 개념 분석(§2~3)은 그대로 유효하다.

---

## 1. 현재 상태

로컬퍼스트 작업이 이 문서의 0~1단계를 대부분 처리했다. 두 문서가 **공통으로
요구하던 것**(불변성·클라이언트 생성 ID·부모 링크·톰스톤)이 그쪽에서 먼저
필요했기 때문이다.

| 영역 | 상태 |
| --- | --- |
| 커밋 불변성 | **완료** — 행을 덮어쓰지 않는다. 수정은 리비전 추가 |
| 콘텐츠 해시 | **완료** — `lib/hash.ts`, `commits.hash`가 PK |
| amend | **완료** — `lib/revision.ts`의 `amendRevision` |
| 톰스톤 삭제 | **완료** — `deleted` 리비전 |
| 소유권 검증 | **완료** — `user_id`는 세션에서만 |
| 마이그레이션 기반 | **완료** — `drizzle/`, `pnpm db:migrate` |
| **참조(스레드)** | **완료** |
| 수정 이력 화면 | **완료** — `/commit/[note_id]/history` |
| 해시 URL | 미착수 (지금은 `/commit/[note_id]`) |
| refs/브랜치 | 보류 — 동기화가 목적이면 불필요 |

즉 **"불변성 → 참조 → 브랜치" 중 앞의 두 칸이 끝났다.** 남은 것은 브랜치인데,
그건 동기화가 목적이라면 필요 없다(§7).

## 2. 핵심 결정 — 은유를 어디까지 밀어붙일 것인가

| 안 | 내용 | 비용 | 결과 |
| --- | --- | --- | --- |
| **A. 얕게** | 부모 컬럼 하나 추가해 답글 트리 | 매우 낮음 | 흔한 트위터 답글. git 색깔은 네이밍뿐 |
| **B. 중간 (권장)** | 커밋 불변 + 콘텐츠 해시 + 부모 참조 + 이름 붙은 ref | 중간 | git의 **핵심 모델**을 그대로 |
| **C. 진짜 git** | blob/tree/commit 객체 저장소, merge, conflict 해소 | 높음 | 메모 앱에는 과잉 |

**권장: B.** 불변 객체·부모 링크·이름 붙은 포인터 3요소만으로 git이 흥미로운
이유(이력이 지워지지 않고, 어느 시점이든 참조되며, 거기서 갈라짐)는 전부
재현된다. merge 없이도 성립한다.

이 중 앞의 둘은 이미 구현됐고, 남은 것이 **부모 참조**다.

## 3. git 개념 ↔ 제품 기능 매핑

| git | 이 앱에서의 의미 | 상태 |
| --- | --- | --- |
| commit | 메모의 리비전 한 개. **불변** | 완료 |
| commit hash | 리비전의 영구 주소 | 완료 (URL 노출은 미착수) |
| `--amend` | 메모 수정 = 새 리비전 | 완료 |
| revert | 톰스톤 삭제 | 완료 |
| parent | **이어 쓰기 대상** | **다음 과제** |
| log | 스레드를 뿌리부터 따라 읽기 | 다음 과제 |
| diff | 리비전 간 내용 비교 | 이후 — 이력 화면은 있으나 비교는 없다 |
| branch (ref) | 이름 붙은 스레드 | 보류 — §7 참고 |
| HEAD / checkout | "지금 이어 쓰고 있는 곳" | 보류 |
| tag | 핀 / 북마크 | 이후 |
| cherry-pick | 다른 스레드의 메모를 인용 | 이후 |
| merge | 두 스레드 합치기 | **버림** |
| conflict | — | **버림** |
| blob / tree | 첨부파일 | 보류 |
| clone / remote / push | 타인 스레드 구독·포크 | 보류 |

merge를 버리는 것이 이 설계의 가장 중요한 생략이다. merge를 포기하면 커밋
그래프가 DAG가 아니라 **트리**로 유지되고, 그 단순화 덕분에 `root_note_id`
하나로 스레드 전체를 인덱스 스캔 한 번에 가져올 수 있다(§5).

## 4. 데이터 모델 — 스레드

### 4.1 두 종류의 "부모"를 섞지 말 것

지금 스키마에는 이미 `parent_hash`가 있다. 여기에 스레드용 부모를 더하면
이름이 겹쳐 헷갈리기 쉬우므로 역할을 못박아 둔다.

| 컬럼 | 의미 | 축 |
| --- | --- | --- |
| `parent_hash` | **같은 메모**의 직전 리비전 | 시간 (수정 이력) |
| `reply_to_note_id` | **다른 메모**에 이어 씀 | 공간 (스레드) |

이 둘은 완전히 다른 관계다. 전자는 "이 글의 예전 모습", 후자는 "이 글이
대답하는 글"이다.

### 4.2 추가할 컬럼

```ts
export const commits = sqliteTable('commits', {
  // ... 기존 컬럼 그대로 ...

  /** 이어 쓰는 대상 메모. 루트면 null */
  reply_to_note_id: text('reply_to_note_id'),
  /** 이어 쓸 당시 그 메모의 리비전. 출처 기록용 */
  reply_to_hash: text('reply_to_hash'),
  /** 스레드 뿌리. 루트 자신이면 자기 note_id */
  root_note_id: text('root_note_id').notNull(),
  depth: integer('depth').notNull().default(0),
})
```

인덱스: `(root_note_id, created)`, `(reply_to_note_id)`.

**`reply_to_note_id`는 리비전이 아니라 메모를 가리킨다.** 이게 이 설계에서
가장 중요한 판단이다. 답글이 특정 리비전 해시에 매달리면, 원본을 수정하는
순간 답글이 "지금의 원본"에서 떨어져 나간다. 스레드 구조는 메모 단위로 잡아야
한다.

그러면서도 **`reply_to_hash`로 "이어 쓸 당시 원본이 어떤 모습이었는지"를 함께
남긴다.** 구조는 `note_id`로, 출처는 `hash`로 — 둘을 나누면 "이 답글이 달린
뒤 원본이 수정되었다"를 화면에서 알려줄 수 있다. 공짜로 얻는 정보다.

`root_note_id`와 `depth`는 비정규화다. insert 시점에 부모로부터 확정되고 이후
변하지 않으므로 불변성을 깨지 않는다.

### 4.3 해시 — 기존 115개를 깨뜨리지 않으려면

새 컬럼도 해시에 들어가야 한다. 그러지 않으면 스레드 구조를 위조할 수 있다.

문제는 `lib/hash.ts`가 고정 포맷이라 필드를 추가하면 **기존 리비전의 해시가
전부 어긋난다**는 것이다. 서버는 push 때만 해시를 재계산하므로 이미 저장된
행은 당장 문제없지만, 같은 내용을 다시 계산했을 때 값이 달라지는 건 콘텐츠
주소로서 바람직하지 않다.

> **해결: 값이 없으면 줄 자체를 넣지 않는다.**
>
> ```
> ...
> created <created>
> deleted <0|1>
> emoji <emoji>
> reply <reply_to_note_id> <reply_to_hash>   ← 루트면 이 줄이 없음
>
> <message>
> ```

루트 메모는 이 줄이 빠지므로 **지금과 정확히 같은 해시가 나온다.** 기존
115건이 그대로 유효하다.

### 4.4 amend 규칙 — 이전 결론을 뒤집는다

이 문서의 초판은 **"답글이 달린 커밋은 수정 불가"** 를 권했다. 근거는
git의 "공개된 히스토리는 rewrite하지 않는다"와 트위터의 관행이었다.

**전제가 바뀌었으므로 이 결론은 철회한다.** 이 앱은 단일 사용자 개인 메모
앱이고, 답글도 내가 단 것이다. 남이 반응한 글을 고치는 상황 자체가 없으므로
"공개된 히스토리" 논리가 성립하지 않는다. 자기 글을 고치는 걸 막을 이유가 없다.

대신 §4.2의 `reply_to_hash`가 그 자리를 대신한다 — 수정을 막는 대신
**"이 답글은 수정 전 내용에 달렸습니다"를 보여준다.** 정보를 지우지 않고
드러내는 쪽이 불변 모델에 더 맞는 답이다.

(구현상으로도 이득이다. 수정 금지는 push 시점에 "답글이 있는가"를 검사해야
하는데, 오프라인에서 답글과 수정이 각각 다른 기기에서 일어나면 판정이
애매해진다. 금지를 없애면 그 문제가 사라진다.)

## 5. 서비스 / 쿼리

`services/Commit.ts`에 더할 것:

```ts
getThread(params)        // root_note_id 기준 스레드 전체
getReplyCounts(params)   // 홈 목록의 답글 수 배지
getHistory(params)       // note_id의 리비전 전체 = 수정 이력
```

기존 `isLatestRevision`(같은 `note_id` 중 최대 `hlc`)은 그대로 재사용한다.

```sql
-- 홈: 이 달에 "뿌리가 있는" 스레드 전체.
-- 월 필터는 뿌리에만 걸고, 답글은 작성월과 무관하게 따라온다(§6).
WITH month_roots AS (
  SELECT note_id FROM commits
  WHERE user_id = ? AND deleted = 0
    AND reply_to_note_id IS NULL
    AND hlc = (SELECT MAX(r.hlc) FROM commits r
               WHERE r.note_id = commits.note_id AND r.user_id = commits.user_id)
    AND strftime('%Y-%m', created) = ?
)
SELECT * FROM commits
WHERE user_id = ? AND deleted = 0
  AND root_note_id IN (SELECT note_id FROM month_roots)
  AND hlc = (SELECT MAX(r.hlc) FROM commits r
             WHERE r.note_id = commits.note_id AND r.user_id = commits.user_id)
ORDER BY created ASC;

-- 스레드 전체 (재귀 불필요 — 트리이고 root_note_id가 비정규화되어 있으므로)
SELECT * FROM commits
WHERE user_id = ? AND deleted = 0 AND root_note_id = ?
  AND hlc = (SELECT MAX(r.hlc) FROM commits r
             WHERE r.note_id = commits.note_id AND r.user_id = commits.user_id)
ORDER BY created ASC;
-- 가져온 뒤 reply_to_note_id로 클라이언트에서 트리를 만든다

-- 수정 이력
SELECT * FROM commits WHERE user_id = ? AND note_id = ? ORDER BY hlc ASC;
```

push 검증에 추가할 것(`services/Commit.ts`의 `push`):

- `reply_to_note_id`가 있으면 그 메모가 **내 소유인지** 확인. 이미 하고 있는
  "타인의 `note_id`" 검사와 같은 이유다.
- `root_note_id`·`depth`가 부모와 일관되는지 확인. 클라이언트가 계산하는
  값이므로 서버가 다시 따져야 한다.
- 부모가 아직 서버에 없을 수 있다(오프라인에서 쓰고 곧바로 이어 쓴 경우).
  기존 `parent_hash`와 같은 이유로 **거절하지 않는다.**

에러 타입은 기존 `NotFoundError` 패턴을 따른다: `ReplyTargetNotFoundError`.

## 6. 화면 / 라우팅

| 경로 | 현재 | 제안 |
| --- | --- | --- |
| `/` | 월별 목록 | **스레드 단위 목록** — 뿌리 아래 답글이 붙어 보인다 |
| `/commit` | 작성 폼 | 그대로 |
| `/commit/[note_id]` | 수정 폼 | **상세 = 스레드 뷰 + 이어쓰기 폼**, 수정은 분리 |
| `/commit/[note_id]/amend` | — | 수정 폼 |
| `/commit/[note_id]/history` | — | 수정 이력 (구현됨) |

지금 `/commit/[note_id]`가 곧바로 수정 폼인 것이 어색하다. 메모를 열었을 때
나와야 하는 것은 수정 폼이 아니라 **그 메모와 거기서 자란 것들**이다.

URL은 `note_id`를 유지한다. 초판은 해시 URL(`/c/[hash]`)을 제안했지만,
해시는 수정할 때마다 바뀌므로 **영구 링크로는 `note_id`가 맞다.** 해시는
이력 화면에서 리비전을 가리킬 때 쓴다(`/commit/[note_id]/history#a1b2c3d`).

### 6.1 홈에 답글을 붙인다 — 월 필터는 뿌리에만 (결정됨)

두 결정을 합치면 규칙이 하나로 정리된다.

> **월 필터는 스레드의 뿌리에만 적용한다. 뿌리가 걸리면 스레드 전체가 따라온다.**
>
> 즉 **스레드는 뿌리가 쓰인 달에 속한다.** 답글이 언제 쓰였든 뿌리 옆에 붙는다.

이 규칙이 좋은 이유는 스레드가 쪼개지지 않기 때문이다. 답글에 월 필터를 그대로
걸면 11월에 시작한 대화의 답글이 12월 화면에만 나타나 맥락이 끊긴다.
메모 앱에서 시간축의 기준점은 **그 이야기를 시작한 시점**이다.

날짜 그룹핑(현재 `CommitList.tsx`의 일자별 sticky 헤더)도 **뿌리 기준**이다.
답글은 자기 날짜로 새 그룹을 만들지 않고 뿌리 블록 안에 자기 시각을 달고
들어간다. 그래서 8월 화면에서 "11월 3일" 그룹 안에 12월에 쓴 답글이 보일 수
있고, 그게 의도한 모습이다.

**받아들이는 대가:** 오래된 메모에 오늘 답글을 달면 이번 달 화면에는 나타나지
않는다(뿌리가 지난달이므로). 실사용에서는 답글 대부분이 원문 직후에 달리므로
드물게 걸리는 경우다. 걸리적거리면 "이번 달에 활동이 있던 스레드도 포함"을
나중에 더할 수 있고, 그때는 스레드가 두 달에 걸쳐 나타나게 된다 — 지금은
단순한 쪽을 택한다.

**뿌리가 삭제된 스레드는 통째로 숨는다.** 뿌리가 톰스톤이면 `month_roots`에
들지 않으므로 답글도 함께 사라진다(데이터는 남는다). 뿌리를 지우는 것은
그 이야기 전체를 접는 것으로 본다.

### 6.2 답글이 많을 때

전부 펼치면 홈이 길어진다. 뿌리 아래 **최근 3개까지만 보이고**, 나머지는
"답글 N개 더 보기"로 스레드 뷰(`/commit/[note_id]`)로 넘긴다.
초판의 "답글 수 배지"는 이 링크가 대신한다.

깊이는 들여쓰기로 표현하되 **시각적으로는 1단계까지만** 들여쓴다. 그 아래는
같은 깊이로 그린다 — 개인 메모의 스레드가 3단 이상 깊어지는 일은 드물고,
계단이 깊어지면 좁은 화면에서 읽기 어려워진다.

## 7. 브랜치(refs)를 보류하는 이유

초판은 `refs` 테이블과 HEAD로 "이름 붙은 스레드"를 3단계에 두었다.

브랜치 아이디어의 실제 동기가 로컬퍼스트였음이 확인됐고, 그쪽에서는 기기별
브랜치가 **구현 세부사항이라 UI로 드러나면 안 된다**는 결론이 났다
([local-first.md §1](./local-first.md)).

제품 기능으로서의 "이름 붙은 스레드"는 여전히 가능하지만, **스레드 자체를
먼저 써 본 뒤 이름이 실제로 아쉬운지 확인하고 판단하는 편이 좋다.**
스레드는 이름 없이도 동작한다.

| 2.5 | 수정 이력 화면 | **완료** |
| 3 | refs / 브랜치 / HEAD | 보류 (§7) |
| 4 | tag · cherry-pick · diff | 이후 |

2단계 작업 순서:

1. 컬럼 4개 추가 마이그레이션 + 기존 115건 백필(`root_note_id = note_id`, `depth = 0`)
2. `lib/hash.ts`에 `reply` 줄 추가 (§4.3 — 루트는 해시 불변)
3. `lib/revision.ts`에 `replyRevision` 추가
4. `services/Commit.ts` — 홈 쿼리를 스레드 단위로(§5), `getThread`, push 검증
5. 클라이언트 — `mergeOutbox`가 대기 중인 답글도 뿌리에 붙이도록 확장
6. 화면 — 홈 스레드 렌더(§6.1~6.2), 상세를 스레드 뷰로, 이어쓰기 폼

5번을 빠뜨리기 쉽다. 지금 `mergeOutbox`는 `note_id` 단위로만 겹치므로,
아직 올라가지 않은 답글은 뿌리를 찾지 못해 목록에서 뜬금없는 자리에 놓인다.
